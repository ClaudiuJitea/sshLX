# sshLX: Architecture Notes (deliverable 1, for review)

Status: reviewed; implementation follows these notes. Corrections found during implementation are marked **[Update]**.
PuTTY base: 0.85, at `../putty-0.85` (read-only, sha256 manifest in
`tools/putty-0.85.sha256`, 722 files).

---

## 0. Summary of findings

1. **No PuTTY overrides were expected** at review time.
   **[Update]** One turned out to be necessary: `unix/serial.c` keeps a
   static fd index that goes stale when a serial session closes (§4,
   `PUTTY-OVERRIDES.md`). Every other source file is compiled unchanged, and
   the rest of their global state does not block many sessions per process.
   PuTTY's own GTK3 `puttyapp` already runs many sessions in one process on
   the same core code.
2. **The front-end contract is small and was measured, not guessed.** I built
   PuTTY's libraries out of tree in a scratch directory, then linked the exact
   object set sshLX plans to reuse with no GTK front-end files. The result is
   **52 unresolved symbols**: 33 `dlg_*` functions plus 19 others (§3.2).
   sshLX also provides three per-session vtables: `Seat`, `TermWin` and
   `LogPolicy`.
3. **`unix/config-gtk.c` needs no GTK** despite its name. It only calls
   `ctrl_*` and needs `about_box()`, so it is reused unchanged. As a result,
   the Unix-specific config panels (fonts, shadow bold, scrollbar side, UTF-8
   override, X11 class name) come from PuTTY's own code.
4. **The main porting work is in `unix/window.c`** (5,754 lines, GTK). Its
   keyboard translation (`key_event`, about 1,000 lines), mouse/selection
   glue, drawing (`do_text_internal`) and clipboard logic must be
   re-implemented. This is the main risk to exact behavioural fidelity (§7).
5. **One decision needs your input: crash isolation (§5).** Running everything
   in one process gives per-session isolation for every error PuTTY reports
   through the Seat: network errors, protocol errors, disconnects, auth
   failures and backend close. A real crash cannot be contained in-process: a
   segfault, a failed PuTTY `assert()` (PuTTY forces assertions on in release
   builds), or `modalfatalbox()` on out-of-memory. Each of those ends the
   whole process.

## 1. Method

- `tools/putty-0.85.sha256` was generated before any other work. It covers
  every regular file under `putty-0.85/` (722 files; there are no symlinks or
  empty dirs).
- `tools/verify-putty-untouched.sh [PUTTY_DIR] [MANIFEST]` checks three things:
  - (a) content, with `sha256sum --strict -c`;
  - (b) no extra files or symlinks;
  - (c) no empty directories, which would come from stray builds.

  Exit codes: 0 = OK, 1 = mismatch, 2 = usage error. I tested it on a scratch
  copy with one modified file plus a stray `cmake.h`, and it caught both. The
  CMake test target is added with the first `CMakeLists.txt` (Phase 0).
- **Probe build** (scratch dir only, outside both trees): first
  `cmake -S putty-0.85 -B <scratch>`, then building the `utils crypto network
  settings eventloop sshclient otherbackends guiterminal charset plink`
  targets. That build succeeded. Afterwards `verify-putty-untouched.sh`
  reported OK, so PuTTY's out-of-tree build writes nothing into its source.
  This also confirms the tree still builds as shipped (CLI targets; GTK3 is not
  installed here, so the full GUI build was not exercised).
- **Link probe**: I linked the chosen object set against an empty `main()` with
  `--warn-unresolved-symbols` and recorded every undefined symbol. I then
  mapped each one to the object files that reference it, using `nm -u`.

## 2. Build plan (how PuTTY sources are consumed)

- `SSHLX_PUTTY_SOURCE_DIR` (cache PATH, default `${CMAKE_SOURCE_DIR}/../putty-0.85`).
- `cmake/putty-sources.cmake` lists every PuTTY file explicitly, by relative
  path. A helper `sshlx_putty_src(<relpath>)` resolves each one: it returns
  `src/putty-overrides/<relpath>` if that exists, otherwise
  `${SSHLX_PUTTY_SOURCE_DIR}/<relpath>`. Overrides are therefore picked up
  automatically, and listed in the configure log.
- **Generated files go in `build/generated/`, never in PuTTY's tree:**
  - `cmake.h`: produced by `configure_file()` from
    `${SSHLX_PUTTY_SOURCE_DIR}/cmake/cmake.h.in`. The template is only read.
    The `check_*` probes from `cmake/setup.cmake` and
    `cmake/platforms/unix.cmake` are re-implemented in
    `cmake/putty-config-checks.cmake`.
  - `sbcsdat.c`: generated by `perl charset/sbcsgen.pl -o build/generated/sbcsdat.c`.
    `charset/enum.c` `#include`s it, so `build/generated` is on the include
    path.
  - `cmake_commit.c`: defines `commitid[]`, which `utils/buildinfo.c` and
    `terminal.c` need. sshLX writes `"unavailable"` plus the sshLX version.
  - `licence.h`: **not needed**; only GTK's `unix/dialog.c` uses it.
- Compile flags for PuTTY and engine C code, matching what PuTTY does:
  - `C_STANDARD 99`
  - `-DHAVE_CMAKE_H`
  - include dirs: `putty/`, `putty/unix`, `putty/charset`, `putty/terminal`,
    `build/generated`
  - **`NDEBUG` stripped**: assertions are security-relevant, and `defs.h` has
    a backstop `#error`
  - `-fmacro-prefix-map`
  - Crypto acceleration objects (`aes-ni.c`, `sha256-ni.c`, `sha1-ni.c`,
    `aesgcm-clmul.c`, and the NEON variants) are built as separate object
    libraries with their own `-msse4.1 -maes ...` flags. The feature tests are
    re-implemented from `crypto/CMakeLists.txt`.
  - Note: with GCC 15 a non-C99 build warns that `unreachable` is redefined
    (C23 `<stddef.h>`). Pinning C99 avoids this, as PuTTY's build does.
- `be_list.c` is not compiled. PuTTY builds it per program, and sshLX's
  `src/engine/engine_backends.c` takes its place: `backends[]` = SSH, Serial,
  Telnet, Rlogin, SUPDUP, Raw, SSH-connection (bare) (what `be_list.c` gives
  with `SSH=1 SERIAL=1 OTHERBACKENDS=1`), plus sshLX's local shell
  (`engine_shell.c`, protocol 64, id `localshell`). That back end does not use
  PuTTY's `unix/pty.c`: its SIGCHLD handler reaps every child with
  `waitpid(-1)`, Qt's included; `engine_shell.c` waits for its own shell
  through a pidfd. `appname` changes only user-visible
  strings such as titles. The storage dir is hard-coded to `putty` in
  `unix/storage.c`, so sessions stay at `~/.config/putty` / `~/.putty`.
- GSSAPI: `PUTTY_GSSAPI=DYNAMIC` behaviour (dlopen of libgssapi_krb5 at
  runtime) needs no krb5 headers at build time. Exposed as `SSHLX_GSSAPI`.
- **Header-override caveat (for rule 5.3):** a `.c` file that does
  `#include "foo.h"` finds `foo.h` in its own directory before any `-I` path.
  So an overridden header only takes effect for files outside its directory.
  Any same-directory `.c` that includes it would need overriding too. No header
  overrides are planned.

(`unix/serial.c`, **[Update]**). Everything else is handled in sshLX's front
end. PuTTY is
single-threaded, and so is the engine: every engine call must be made on the
thread that called `sshlx_engine_init()` (the Qt GUI thread). The engine
asserts this in debug builds.

## 5. Crash isolation: **decision needed**

The requirement says "Closing, disconnecting **or crashing** the backend of
one tab never affects other tabs."

**In-process (current plan):**
- Closing, disconnecting, network errors, protocol errors, auth failures and
  remote exit all arrive through `seat_connection_fatal` /
  `notify_remote_exit` / `backend_exitcode`, all per session. One tab is
  torn down (`ldisc_free`, `backend_free`, `term_provide_backend(NULL)`,
  callbacks deleted) while the others keep running. This mirrors
  `destroy_inst_connection()` in `window.c`.
- *Not* containable in-process:
  - segfaults or memory corruption;
  - PuTTY `assert()` failures, which are deliberately on in release builds;
  - `modalfatalbox()` (out of memory, terminal internal errors), which is
    `NORETURN`.

  Recovering from any of these in-process (`longjmp`, catching signals) would
  leave PuTTY's shared trees and crypto state undefined. That is a security
  regression, so I won't do it.

**Option B: session host process (later, optional).** Each tab runs the same
engine in an `sshlx-session` child process (sshLX's own binary, not PuTTY).
The engine API is shaped so this stays possible: all callbacks carry plain
data, there are no pointers into engine memory except opaque handles, and
prompts are async. The API would then be serialised over a socketpair. Costs:
- rendering traffic goes over IPC;
- clipboard and prompts are proxied;
- settings dialogs need the Conf to travel between processes;
- significantly more work and latency.

**Recommendation:** go in-process for Phases 0–5, and document the residual
limit (a true crash ends the app, as it would end a PuTTY window).
Additionally:
- On abnormal exit, a crash handler writes a breadcrumb.
- "Restore sessions on startup" then offers to reopen the tabs.

Option B can be added as Phase 6 if you want hard isolation. **Please confirm
or choose B now**, since B would change Phase 0's design.

## 7. Known/expected behaviour differences from PuTTY 0.85 (GTK)

All of these come from the tabbed UI or from Qt. None affects protocol or
security behaviour.

1. **Server-initiated window ops** (`request_resize` from DECCOLM/`ESC[8t`,
   `move`, `set_minimised/maximised`, `set_zorder`):
   - in a docked tab, resize is not possible, so it is answered with
     `term_resize_request_completed()` and the terminal keeps its tab size.
     This is the path PuTTY itself takes when it can't resize, for example
     when maximised.
   - in a floating tab window they are honoured.
   - move, minimise and z-order only apply to floating windows.
2. **Named custom clipboards** (`CLIP_CUSTOM_1..3`, i.e. arbitrary X selection
   atoms, enabled by `NAMED_CLIPBOARDS`): Qt only exposes CLIPBOARD and
   PRIMARY (and PRIMARY on Wayland only with
   `zwp_primary_selection`/`wp_primary_selection`). Custom atoms will be
   treated as CLIPBOARD and the settings UI will say so. CLIPBOARD and PRIMARY
   behave as in PuTTY.
3. **X server fonts** (`server:` FontSpecs): not rendered (allowed by the
   spec). They fall back to the closest client font with a warning, and the
   stored setting is **not** rewritten unless you change it, so PuTTY still
   reads it the same way.
4. **Keyboard**: re-implemented from `window.c` `key_event` on Qt key events.
   Every Conf keyboard option is kept: backspace, home/end, function-key
   modes, cursor/keypad application modes, NetHack keypad, AltGr/Alt-is-Meta,
   Ctrl-Alt, compose, and `osx_*_meta`. Exactness risk: GTK delivers X keysyms
   and Qt delivers `Qt::Key` plus native scan codes and virtual keys. On X11
   and on Wayland (`xkb`), `nativeVirtualKey()` is the keysym, so the port can
   key off the same values. This will have a table-driven test comparing
   generated byte sequences to PuTTY's expected output for each
   option/modifier combination.
5. **CloseOnExit**: PuTTY closes the window; sshLX's default is "keep tab with
   reconnect bar", with an option to restore exact PuTTY behaviour. The Conf
   value is still read and stored unchanged.
6. **Host-key and weak-crypto prompts** are in-tab overlays instead of modal
   windows. They show the same text (from `SeatDialogText`), the same three
   choices, and the same "More info" (fingerprints, full key).
7. **Window title / icon title**: the tab shows the window title. Icon title
   (`set_icon_title`, `WinNameAlways`) is kept but only shown as a tooltip.
8. **"Change Settings" mid-session**: same `midsession=true` control box and
   same reconfig path (`term_reconfig`, `backend_reconfig`, `ldisc_configure`,
   `log_reconfig`, pinger).

## 8. Engine design

### 8.1 Host loop

PuTTY needs fd readiness (`uxsel`), one wall-clock timer (`timing.c`), and a
"callbacks pending" notification (`callback.c`). The Qt app implements:
- `watch_fd` → `QSocketNotifier` (Read/Write/Exception)
- `set_timer` → single-shot `QTimer`
- `wake` → `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`

It then calls back into the engine. No GLib assumptions.
`sshlx_fd_t` is `intptr_t`, so a future Windows host loop can pass
`HANDLE`/`SOCKET` values.

### 8.2 Session lifecycle (mirrors `window.c`)

`create`:
1. `conf_copy`, `init_ucs` (`unix/unicode.c`), `term_init`, `log_init`,
   `term_provide_logctx`, `term_size`.

`connect`:
1. `seat_set_trust_status(true)`
2. `backend_init(backend_vt_from_proto(protocol), ...)`
3. `term_setup_window_titles`
4. `term_provide_backend`
5. `ldisc_create`, which emits `STATE_CONNECTING`.

`disconnect`: `ldisc_free`, `backend_free`, `term_provide_backend(NULL)`,
then emits `STATE_DISCONNECTED` and keeps the terminal and scrollback.

`reconnect`: `connect` again on the same Terminal, as GTK's "Restart Session"
does.

`destroy`:
1. disconnect
2. `term_free`, `log_free`, `conf_free`
3. `delete_callbacks_for_context` and `expire_timer_context` for every context
   object
4. cancel pending prompts
5. free.

Destroy is safe to call from inside an engine callback: it is deferred to a
toplevel callback, as GTK does with `exit_callback`.

### 8.3 Rendering

As in GTK's backing-surface model:
- `term_update` / `term_paint` produce `draw_text` / `draw_cursor` /
  `draw_trust_sigil` calls between `begin` and `end`.
- The Qt widget paints those into a per-session backing `QImage` (at device
  pixel ratio), then calls `update(rect)`.
- `paintEvent` only blits the image.
- Expose and resize call `sshlx_session_paint(rect)`.

The engine decodes PuTTY's packed `attrs` / `truecolour` into an explicit
struct: RGB fg/bg after palette, reverse, dim and bold-as-colour rules;
flags; wide; combining; DEC line-drawing already translated; and line
attributes for double width/height. That way the UI never needs PuTTY's bit
layout. The 262-entry palette (from `palette_set`) lives in the engine.

### 8.4 Settings dialog bridge

- `setup_config_box(b, midsession, protocol, protcfginfo)`,
  `unix_setup_config_box`, `gtk_setup_config_box` (PuTTY's own, from
  `config-gtk.c`) and `ctrlset_normalise` build the `controlbox`.
- The engine exports a read-only description to the UI: panel paths, sets,
  controls with type (text, editbox, radio, checkbox, button, listbox,
  fileselect, fontselect, columns), labels, shortcuts, radio/list options,
  column layout, and editbox `has_list`/password flags.
- `fe_dlg.c` keeps C-side state for every control (string, int, checked,
  list items, selection). The `dlg_*` functions read and write that state and
  emit "control changed" notifications to the UI.
- UI edits come back as `sshlx_dlg_set_*` followed by `sshlx_dlg_activate`,
  which runs `ctrl->handler(ctrl, dlg, data, EVENT_VALCHANGE/ACTION/...)`
  exactly as GTK does.
- So every PuTTY option is reachable without hand-writing it, and PuTTY's
  own handlers keep doing the Conf writes. That includes the "Load / Save /
  Delete" session list, the colour editor, port-forward list, kex/cipher
  priority lists, and "Manage host CAs".
- The property grid is a separate, direct view built from `conf_key_info[]`,
  which PuTTY already exports: 211 keys, each with value and subkey type,
  default, save keyword and enum map. That covers 101 bool, 68 int, 29 str,
  3 str_ambi, 6 filename and 4 font keys, 10 of them keyed.

Notes on the API:
- **Fonts**: the engine stores FontSpec names verbatim (`client:Monospace 12`).
  The Qt side parses `client:<Pango description>` into `QFont` and writes the
  same syntax back, so the saved files stay PuTTY-compatible.
- **Serial auto-detect** lives in `src/platform/serialdetect/` with its own
  plain C header. It builds a `sshlx_conf` (protocol = serial, `SerialLine` =
  the by-id path, plus speed, data bits, parity, stop bits and flow control)
  and uses the same session API. The engine has no udev dependency.
- **EACCES**: `connection_fatal` carries `sys_errno` when the backend error
  came from `open()`. `unix/serial.c` returns the `strerror` text; the engine
  records errno around `backend_init` for serial. The UI shows the
  `dialout`/`uucp` group explanation.

## 10. Risks / open questions for review

1. **Crash isolation**: choose in-process (recommended) or a per-tab session
   host (§5).
2. **Keyboard fidelity** (§7.4): the biggest porting job. Plan: port
   `key_event` into `fe_keyboard.c` in C, using Conf plus PuTTY's own
   `format_*_key` helpers from `terminal.c`, and test it against a captured

## 11. [Update] Implementation notes (after Phases 0–5)

### 11.1 Engine API: differences from the §9 draft

`src/engine/sshlx_engine.h` is the source of truth. The changes from the
reviewed draft:

- **Dropped `char_width`.** As GTK, wide characters use a separate font and
  the callback always returned 1.
- **Cursor drawing split in two.** The cell is drawn with `draw_text`; the
  shape (underline, vertical bar, passive outline) comes from
  `draw_cursor_shape`. This is the logic of `gtkwin_draw_cursor`.
- **`sshlx_session_key()` returns a result code.** The code includes
  font-bigger / font-smaller, so GTK's Ctrl+< / Ctrl+> reach the UI.
- **Whole-Conf text serialisation replaced by per-key transfer.**
  `sshlx_conf_key_export/import/copy/equal` build on PuTTY's own
  `conf_serialise()` format, minus the build-specific key index. They carry
  every subkey, e.g. all port forwardings.
- **Additions:**
  - `sshlx_session_reconfig_conf()`, PuTTY's `term_pre_reconfig`;
  - `sshlx_conf_has_key()`; the getters never abort on an absent key. PuTTY's
    `conf_get_*` assert presence, and a few keys are only set in some
    configurations.
  - `sshlx_engine_set_fatal_handler()`, for the crash breadcrumb;
  - `sshlx_session_send_raw()`;
  - `sshlx_dlg_set_visible_path()`.
- **Passwords:** the opt-in password hook offers one hidden prompt to the
  UI per connection attempt, then falls back to PuTTY's in-terminal prompt.

### 11.2 Isolation: what is and isn't contained

- **Contained per session:**
  - network, protocol and authentication failures;
  - remote exit;
  - serial unplug and serial I/O errors (via the `unix/serial.c` override);
  - closing a tab;
  - SSH, Telnet, Raw and serial sessions running side by side.

  Tested by `engine_sessions_test` and `app_gui_test` (12 tabs, closing and
  failing several).
- **Still process-wide, by design (§5):**
  - segfaults;
  - PuTTY `assert()` failures;
  - `modalfatalbox()` (out of memory).
- **Remaining `exit()` calls in compiled PuTTY sources** (audited):
  - `unix/noise.c`: no entropy source at all. Correctly fatal.
  - `unix/utils/{cloexec,nonblock,block_signal}.c`: `fcntl`/`sigprocmask`
    failing on a valid fd. Practically impossible.
  - `unix/agent-client.c`: `socket(PF_UNIX)` failing, i.e. fd exhaustion.
    Mitigated by raising `RLIMIT_NOFILE` to the hard limit at startup.
- **Crash breadcrumb:** `~/.config/sshLX/open-tabs.crash` is kept up to date
  while running and removed on clean exit. If it's present at startup,
  sshLX offers to reopen the tabs, and shows the last PuTTY fatal message
  if there was one.

### 11.3 Behaviour notes (additions to §7)

- **Server resize requests:** answered with `resize_done` and not
  honoured, in docked *and* floating tabs. The tab or window size decides
  the terminal size.
- **Window operations:** minimise, maximise, move and z-order requests from
  the server are ignored.
- **Serial auto-connect template:** 115200 8N1 with **no flow control**.
  PuTTY's own default is XON/XOFF, which would swallow ^S/^Q on typical USB
  consoles; it's editable per device rule.
- **Keyring:** `libsecret-1-dev` is required at build time for the fetched
  QtKeychain (GNOME Keyring / Secret Service); configure fails without it
  unless `-DSSHLX_KEYCHAIN=OFF`, because the result would fail every keyring
  job on GNOME. QtKeychain's plaintext fallback is never enabled.
- **Qt ADS** is built with a patch (`cmake/patches/qtads-public-x11.cmake`).
  It removes the need for Qt's private headers, and fixes an ADS
  use-after-free in a deferred `ensureWidgetVisible` when tabs are closed in
  quick succession. The GUI test suite triggered it.
- **Tests** (`tests/`, with PuTTY's `uppity` and `puttygen` as fixtures)
  were removed from the repository in 0.6; they remain in the git history
  before v0.6. The `verify-putty` build target still checks that the PuTTY
  tree is untouched.

### 11.x Automation and transfers through the terminal (0.7.3)

- **ModemTransfer** (model library) speaks Xmodem, Xmodem-1K, Ymodem and Zmodem
  over the same raw session path as file transfer tabs, but switched on and off
  in a live terminal session. Input is queued in `feed()` and handled from a
  timer because `output_data` must not send. Output goes to the terminal again
  when `finished` fires. Zmodem headers are looked for in normal output across
  chunk boundaries, and only ever lead to a question to the user.
- Zmodem's ZCOMMAND, which asks the receiver to run a program, is refused and
  ends the transfer. Received names pass `safeFileName()`, never replace a file,
  and appear only when complete (`.part` until then).
- **TftpServer** is plain QUdpSocket code. Each transfer has its own socket, as
  TFTP requires. `resolve()` confines every path to the folder, links included.
  `setcap` on the binary is not offered as a fix for port 69: file capabilities
  make the loader ignore `$ORIGIN`, so sshLX's private libraries would not load.
- **LogonRunner** is a small expect loop over `OutputText`, which is also what
  scripts read. Steps live on the node in `connections.json`, and a connection
  with none uses its nearest folder's. Passwords never pass through it: it asks
  SessionWidget, which reads the keyring only at a line that looks like a prompt.
- **ScriptHost** runs `python3` as a separate process rather than embedding
  Python, so packages gain no libpython dependency and a script crash can't take
  sessions down. JSON lines over a QLocalServer socket in a private temporary
  directory, with a one-time token in the environment. `resources/python/sshlx.py`
  is copied beside the socket and put on PYTHONPATH.
- The **Command Window** and **button bar** are QMainWindow's own QDockWidget and
  QToolBar, not ADS docks: session tabs must not be able to land in them, and
  saved ADS layouts stay valid.
- **Workspaces** are JSON files holding `openTabEntries()` and the ADS layout, so
  they share the startup restore path.

### 11.y Working across tabs (after 0.7.3)

- **Live typing** replays the engine key event on each target with
  `sshlx_session_key`, so each tab applies its own keyboard settings.
- **Locking** is a flag on SessionWidget and TerminalView of its own: the input
  block that pushes and transfers use comes and goes by itself.
- **Key mappings** are checked before the engine and in ShortcutOverride, so they
  beat application shortcuts. "Send next shortcut to terminal" bypasses them.
- **ScriptRecorder** keeps nothing typed at a line that looks like a password
  prompt. Hidden prompts have no other signal available to the UI.
- Scripts' `wait_for` buffer starts from the cursor's line and is cleared by each
  send, so a prompt on screen counts and an old prompt can't answer a new command.
- **Log rotation** closes PuTTY's log with `log_reconfig` on a private copy of the
  Conf (`sshlx_session_log_set_paused`), renames the file and reopens it in append
  mode. `xlatlognam` is private to PuTTY, so `LogRotate::expandName` repeats its
  rules. With `&T` in the name each rotated log gets a new name anyway.
- Importing a connection tree clears logon scripts: a shared file must not be able
  to run a program when a connection opens.

### 11.z Connect bar, command line and the rest (after 0.7.3)

- **Command line:** subcommands of the same binary, decided before any
  QApplication exists, so they need no display. CliSession is a plain engine
  session with no terminal. Host key questions go to `/dev/tty` and are refused
  when there is none, so a script can't connect to an unknown host by accident.
- `stderr_data` is an engine callback for raw mode. Without it, the remote's stderr
  goes to a terminal that the command line doesn't have.
- **Links:** `Exec=sshLX %U`. A QLocalServer in the runtime directory hands targets
  to a running window. Only targets without a scheme may match saved connections,
  so a web page's link can't reach a stored login.
- **Kermit** uses 94-byte packets and the one-character checksum, with no streaming.
  Server commands, among them running programs, are refused.
- **Zmodem resume** keeps `NAME.part` and asks the sender for a CRC of that many
  bytes (ZCRC) before trusting it. A mismatch or no answer restarts from zero.
- **Cipher names** come from PuTTY's event log, the only place it reports them, so a
  rewording in a later PuTTY shows as blank status rather than a failure.
